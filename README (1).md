# output-governor

**Make every model return the shortest complete answer the task can use.**

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)
[![Python 3.11+](https://img.shields.io/badge/python-3.11%2B-blue.svg)](https://www.python.org/downloads/)
[![PRs welcome](https://img.shields.io/badge/PRs-welcome-brightgreen.svg)](CONTRIBUTING.md)

`output-governor` is a provider-neutral control layer for LLM response cost. It assigns an answer contract and output-token budget to each request, maps that contract to provider controls, watches supported streams for a safe stopping point, validates completeness, and records the result in a savings ledger.

It is designed to compose with [`token-governor`](https://github.com/mentorsurge/token-governor):

- `token-governor` reduces tool-result tokens going into the model.
- `output-governor` controls tokens generated by the model.
- One task budget and one ledger show the full bill.

## Why output tokens matter

Output tokens often cost more than input tokens. The exact ratio depends on the provider, model, context tier, caching, and date. Current official examples include ratios around 5x, 6x, and 8x. Treat "3 to 5 times" as a useful rule of thumb, not a universal price law.

Official pricing sources:

- OpenAI API pricing: https://openai.com/api/pricing/
- Anthropic model pricing: https://docs.anthropic.com/en/docs/about-claude/models
- Gemini API pricing: https://ai.google.dev/gemini-api/docs/pricing

A global `max_tokens=300` is not enough. Three hundred tokens may be wasteful for a classification and unsafe for a deployment plan. The budget has to match the task and answer shape.

## The control loop

```text
application request
       |
       v
+------+------------------+
| classify task and risk  |
+------+------------------+
       |
       v
+------+------------------+       +-------------------+
| build answer contract   | ----> | task budget state |
| fields, length, format  |       +-------------------+
+------+------------------+
       |
       v
+------+------------------+
| provider adapter        |
| max output, verbosity,  |
| stop and response shape |
+------+------------------+
       |
       v
+------+------------------+
| LLM stream or response  |
+------+------------------+
       |
       v
+------+------------------+
| safe-stop controller    |
| + completeness checks   |
+---+-----------------+---+
    |                 |
    v                 v
usable answer     repair or fail open
    |
    +---------------------> savings ledger
```

## The key difference

Post-processing a completed answer cannot refund tokens the provider already generated. It can save downstream context tokens, but the current generation bill is already set.

`output-governor` keeps three savings categories separate:

1. **Realized savings**: tokens the provider did not generate because of preflight limits, provider-native verbosity controls, model routing, or a supported streaming stop.
2. **Downstream savings**: tokens removed before the answer is stored, displayed, or sent into another model call.
3. **Potential savings**: what a shadow run or post-processor says could have been avoided. No money claim until an enforced run proves it.

That accounting rule is part of the product, not a footnote.

## What makes it different

The reviewed market has good gateways, routers, caches, and observability tools. It also has direct output-compression projects. The opening is a tighter control loop:

- Per-task answer contracts instead of one global token cap
- Provider-neutral budget translation
- Structural and semantic safe-stop checks for streaming
- Completeness validators for each task type
- Repair inside the original budget when possible
- Fail-open behavior when confidence is low
- Realized, downstream, and potential savings kept separate
- Shadow mode, replay evaluation, and quality gates
- Shared budgets and ledgers with `token-governor`

This combination was not the main documented workflow of the products reviewed in September 2026. That is a scoped research conclusion, not a claim that nobody has built any part of it.

## Answer contracts

An answer contract defines what "complete" means before the model starts.

```yaml
contract: incident_summary
format: markdown
budget:
  target_tokens: 180
  hard_tokens: 260
required:
  - root_cause
  - impact
  - next_action
constraints:
  max_bullets: 6
  no_preamble: true
  preserve_code: true
risk: medium
on_incomplete: repair_with_remaining_budget
```

Built-in contract families planned for the MVP:

| Task | Default shape | Main completeness check |
|---|---|---|
| Classification | Label plus optional reason | Allowed label exists |
| Extraction | JSON or typed fields | Required fields and types |
| Direct answer | Short prose | Question answered, no unfinished clause |
| Summary | Bullets or sections | Required topics covered |
| Code | Code block plus minimal notes | Syntax closes and requested entry point exists |
| Plan | Ordered steps | Required decisions and next action present |
| Tool decision | Structured tool call | Valid schema and required arguments |
| Long-form | Section budget | Required outline sections complete |

High-risk tasks default to conservative budgets and no semantic early stop.

## Quickstart

Target install after the MVP is built:

```bash
python -m pip install output-governor
```

Library wrapper:

```python
from output_governor import Governor, GovernorConfig

config = GovernorConfig.from_yaml("output-governor.yaml")
governor = Governor(config)

response = governor.generate(
    provider="openai",
    model="gpt-5",
    messages=messages,
    task_id="support-42",
    contract="direct_answer",
    budget={"target_tokens": 120, "hard_tokens": 180},
)

print(response.content)
```

OpenAI-compatible proxy:

```bash
output-governor proxy --config output-governor.yaml --listen 127.0.0.1:8788
```

Then point an OpenAI-compatible client at the local proxy.

## Provider controls

Adapters use the strongest control each provider actually supports:

- Maximum output tokens
- Native verbosity or reasoning controls when available
- Structured response schema
- Stop sequences when structurally safe
- Streaming cancellation when the API and contract permit it
- Model routing when configured
- Prompt-side answer instructions as the portable fallback

The adapter records which control was requested, accepted, ignored, or unavailable. Provider support must be tested, not assumed.

## Safe stopping

A raw token counter should not cut a sentence, JSON object, code block, citation, or required section in half.

The stream controller watches:

- Token budget and remaining reserve
- Sentence and paragraph boundaries
- JSON, XML, Markdown, and code-block closure
- Required contract fields
- Finish reason and provider usage
- Repetition and filler signals
- Stop confidence

The MVP only stops early when structural checks pass and contract completeness is high enough. Otherwise it lets the hard provider limit or normal completion finish the answer.

## Savings ledger example

```text
Task: support-42
Contract: direct_answer
Provider/model: openai / gpt-5

Baseline source: replay median
Baseline output tokens:      612
Actual output tokens:        164
Realized tokens avoided:     448
Downstream tokens removed:     0
Potential tokens avoidable:    0
Estimated output cost: $0.00612 -> $0.00164
Estimated realized savings: $0.00448

Completeness score:          1.00
Structure valid:              yes
Repair calls:                   0
Stop reason:        semantic_safe_stop

Measured: actual tokens, structure, stop, latency
Estimated: baseline counterfactual and dollar values
```

A baseline is a counterfactual. It must name its source, such as an A/B control, replay median, or shadow observation. Without a baseline, the ledger reports actual spend but not tokens avoided.

## Design rules

- Control generation before trimming completed text.
- Never call post-generation trimming current-call savings.
- Define completeness before enforcing brevity.
- Prefer provider-native controls, then portable instructions, then safe stream cancellation.
- Fail open when a validator is uncertain.
- Never cut structured output at an invalid boundary.
- Keep exact numbers, identifiers, citations, code, and user constraints.
- Do not spend more on judging an answer than the output savings can justify.
- Separate visible answer tokens from hidden reasoning tokens when the provider reports both.
- Record every intervention and fallback.

## Measured vs inferred

### Measured directly

- Actual output tokens reported by the provider
- Visible and reasoning tokens when separately reported
- Latency and time to first token
- Finish reason and cancellation result
- Structure validity
- Required-field coverage
- Repair count
- Actual provider charge when supplied by the provider

### Estimated or inferred

- Tokens avoided against a replay, shadow, or control baseline
- Dollar savings calculated from a configured price
- Semantic completeness scores
- Task type when classified automatically
- The rule of thumb that output tokens cost 3 to 5 times input tokens
- Competitive differentiation beyond the reviewed products and pages

## Failure behavior

- Unknown task: use a conservative generic contract.
- Adapter cannot enforce a requested control: record it and use the portable fallback.
- Stream cannot be canceled safely: allow normal completion.
- Structure becomes invalid: stop enforcement and repair within reserve or return the original.
- Completeness is uncertain: fail open.
- Ledger fails: return the answer with a warning unless strict audit mode is enabled.
- Baseline is missing: record actual spend without claiming savings.

## Security and privacy

Prompts and responses may contain private data. Local storage should be the default. Raw capture must have a retention policy and access controls. Normal ledger reports should store hashes and metrics, not full private answers.

Streaming cancellation, provider credentials, and proxy authentication need explicit tests before production use.
